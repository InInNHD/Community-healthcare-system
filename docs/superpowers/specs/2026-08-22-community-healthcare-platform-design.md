# 社区医疗服务完整平台设计规范

**日期：** 2026-08-22

**状态：** 已完成会话设计评审，等待书面规范复核

**适用仓库：** Community healthcare system

## 1. 目标与边界

本项目在现有 Spring Boot + Vue 三门户 MVP 上演进为单个社区卫生服务中心的主业务系统，兼容下属多个社区卫生服务站，并为未来多机构扩展保留稳定边界。

系统负责以下核心业务：

- 居民主索引与电子健康档案。
- 机构、站点、科室、岗位、人员与执业资质。
- 排班、号源、预约、签到、候诊和线下接诊。
- 电子病历、诊断、检查申请与结果归集。
- 处方、药师审核、发药、药品批次及库存追溯。
- 家庭医生团队、签约服务包和履约管理。
- 高血压、2 型糖尿病、COPD、65 岁以上老年人健康管理。
- 双向转诊、收费、模拟医保和外部系统适配。
- 管理员、医护、药师、居民门户及全链路审计。

首批版本不开展互联网诊疗。居民端可提供预约、报告查询、签约、随访、指标上报和健康咨询留言，但诊断与处方必须由医务人员在线下接诊后生成。

生产环境从空库启用。旧系统仅作为历史只读系统保留，不进行自动或一次性数据迁移。Demo 模式继续使用虚构数据，并保留管理员、医生、护士、居民四个账号的密码预填；Demo 不得连接生产数据库或使用生产密钥。

## 2. 核心设计原则

1. 采用模块化单体，不在首期拆分微服务。
2. 按可工作的纵向业务闭环交付，不按数据表批量铺设 CRUD 页面。
3. 后端维护一套权威领域数据，三个门户只提供不同权限视图。
4. 医疗记录、财务和库存均以不可变业务流水或版本记录为依据，不允许直接覆盖结果字段充当账本。
5. 业务规则、随访频次和提示阈值必须版本化并记录来源，不在前端硬编码临床结论。
6. 外部系统通过端口—适配器接入；首版使用可审计模拟实现，取得当地规范和联调环境后替换适配器。
7. 真实居民数据上线前必须完成最小权限、敏感数据保护、访问审计、备份恢复和真实 MySQL 质量门禁。

## 3. 总体架构

### 3.1 后端模块

继续使用一个 Spring Boot 可部署单元，内部划分以下业务模块：

| 模块 | 责任 |
| --- | --- |
| `identity-org` | 账号、角色、机构、站点、科室、人员、岗位和执业资质 |
| `resident-registry` | 居民主索引、多标识、家庭、监护关系、授权与更正申请 |
| `scheduling` | 排班、号源、预约、改约、签到、候诊和爽约 |
| `clinical` | 接诊、病历、诊断、过敏、问题、检查医嘱和结果归集 |
| `pharmacy` | 处方、药师审核、调配、发药、退药、批次和库存流水 |
| `family-doctor` | 家庭医生团队、签约、服务包、履约任务和评价 |
| `public-health` | 高血压、糖尿病、COPD、老年人管理及通用随访任务 |
| `referral` | 转出、接收、预约、到诊、反馈、下转和关闭 |
| `billing` | 收费目录、账单、支付、退费、模拟医保和对账 |
| `notification` | 站内消息、预约提醒、随访提醒和短信适配 |
| `integration` | 区域平台、医保、LIS/PACS 和历史系统只读适配器 |
| `audit` | 登录、访问、变更、导出、签署和紧急授权审计 |

每个模块内部使用 `domain / application / infrastructure / api` 结构：

- `domain` 保存聚合、值对象、状态机和领域服务，不依赖 Web 或数据库实现。
- `application` 组织用例、事务边界、权限上下文和模块公开接口。
- `infrastructure` 实现数据库、缓存、对象存储、消息和外部适配器。
- `api` 提供 HTTP DTO、参数校验和响应映射，不直接暴露 JPA 实体。

模块之间只能调用公开应用接口或订阅领域事件，不得直接访问其他模块的 Repository。使用 ArchUnit 测试阻止越界依赖。跨模块保存稳定业务 ID，不建立跨模块 JPA 对象图。

### 3.2 数据与事件

使用一个 MySQL 8 数据库和一组 Flyway 迁移，按业务前缀区分表：

- `iam_*`、`org_*`
- `person_*`
- `sched_*`
- `clinical_*`
- `rx_*`、`inventory_*`
- `fd_*`、`ph_*`
- `referral_*`
- `billing_*`
- `integration_*`
- `audit_*`

需要通知或外部集成的业务事务同时写入 `outbox_event`。后台发布器在提交后投递事件，按幂等键重试；持续失败的事件进入死信状态并由集成工作台人工处理。业务成功不依赖短信、区域平台或模拟医保同步成功，但必须保留待同步状态和追踪编号。

### 3.3 前端结构

Vue 3 前端拆为三个独立构建入口：

- `resident-web`：公网居民门户。
- `staff-web`：内网或 VPN 医生、护士、药师工作台。
- `admin-web`：内网或 VPN 管理与运营门户。

三端共享设计令牌、基础组件、错误模型和由 OpenAPI 生成的 TypeScript 客户端。门户之间不共享业务状态，不通过隐藏菜单代替后端鉴权。

### 3.4 部署边界

居民端通过 HTTPS、WAF 和公网限流访问；管理端和医护端仅允许机构内网或 VPN。反向代理阻止公网访问内部 API 和敏感 Actuator，应用层再次执行门户、角色与数据范围校验。

开发和 Demo 保持单实例可运行。生产支持至少两个无状态应用实例；会话和限流状态存入 Redis；定时任务使用数据库锁避免重复执行。MySQL、Redis、对象存储和管理端口不暴露公网。

## 4. 核心领域模型

### 4.1 身份、组织与居民

- `Organization`：社区卫生服务中心，保留未来上级机构和多机构扩展字段。
- `Site`：中心本部或下属服务站。
- `Department`：科室。
- `Staff`：工作人员主档。
- `Credential`：医生、护士、药师等执业资质、执业范围和有效期。
- `CareTeam`、`CareTeamMember`：家庭医生团队及成员。
- `Person`：自然人基础身份。
- `Patient`：居民医疗身份和不可变患者号。
- `PatientIdentifier`：身份证、医保码、旧系统号等标识。
- `Household`、`GuardianRelationship`：家庭与监护关系。
- `Consent`：授权目的、数据范围、有效期、撤回状态和证据。
- `AppUser`：登录账号，可关联 Patient 或 Staff，但不承载临床资料。

姓名、性别、出生日期和身份标识属于主要身份字段。居民只能提交更正申请，由授权人员复核；电话、联系地址等联系方式可由居民自行维护并记录变更审计。

### 4.2 排班与预约

核心模型包括 `ScheduleTemplate`、`ScheduleSession`、`Slot`、`Appointment`、`CheckIn` 和 `QueueEntry`。

号源状态：

```text
未发布 → 可预约 → 已占用 → 已使用
                  └→ 已释放
可预约/已占用 → 停诊
```

预约状态：

```text
待确认 → 已确认 → 已签到 → 接诊中 → 已完成
   └────────→ 已取消               └→ 爽约
```

占号必须使用数据库原子操作或唯一约束，保证同一号源不能被重复预约。所有创建请求支持 `Idempotency-Key`。取消和改约保存操作人、原因、时间及原号源释放记录。

`FutureOrPresent` 只用于创建和改约命令，不放在会随时间自然变成历史数据的持久化实体字段上。预约只有在关联接诊记录完成签署后才能进入已完成状态。

### 4.3 接诊与电子病历

核心模型包括 `Encounter`、`ClinicalNote`、`Diagnosis`、`Problem`、`Allergy`、`Observation`、`Order`、`DiagnosticReport` 和 `ClinicalDocumentVersion`。

接诊记录状态：

```text
草稿 → 医师签署 → 补记/更正
              └→ 作废
```

已签署病历不可原地覆盖。补记和更正创建新版本，保存原内容摘要、修改内容、修改人、时间和原因。作废不会物理删除记录。护士可记录生命体征和护理内容，但不能签署诊断和处方。

### 4.4 处方、药房与库存

核心模型包括 `Prescription`、`PrescriptionItem`、`PharmacyReview`、`Dispense`、`MedicineSku`、`MedicineBatch`、`Warehouse` 和 `InventoryTransaction`。

处方状态：

```text
草稿 → 医师签署 → 待药师审核
                    ├→ 已通过 → 配药 → 核对 → 发药
                    └→ 已驳回
已签署/已通过 → 作废
```

处方项目保存诊断关联、药品、剂量、频次、给药途径、疗程和用药指导。审方至少检查过敏、重复用药、剂量范围、相互作用扩展点和诊断一致性。发药关联药品批次并生成不可变库存流水。

库存余额由入库、出库、发药、退药、盘点、报损和调拨流水汇总，不允许通过普通更新接口覆盖库存。每条流水包含业务单据、操作人、原因、调整前后数量和幂等键。

### 4.5 家庭医生与公卫

核心模型包括 `FamilyDoctorContract`、`ServicePackage`、`ServiceItem`、`ServiceTask`、`TaskFulfillment`、`ChronicRegistry`、`FollowUpPlan`、`FollowUpVisit`、`RiskAssessment` 和 `HealthAlert`。

签约状态：

```text
草稿 → 居民确认 → 生效 → 暂停/到期/解约
```

履约任务状态：

```text
待分派 → 已分派 → 执行中 → 已完成
                    ├→ 异常待处置 → 已关闭
                    └→ 逾期/取消
```

通用任务框架负责任务、提醒、逾期、责任人和完成证据；高血压、2 型糖尿病、COPD、老年人年度管理分别使用专属随访表和校验规则。规则保存 `ruleCode`、`version`、`effectiveFrom`、`effectiveTo`、政策来源和本地覆盖记录。

规则只产生辅助提示、复测建议、转诊建议和医护待办，不自动形成诊断或处方。

### 4.6 转诊、收费与外部集成

转诊状态：

```text
草稿 → 知情同意 → 已提交 → 已接收 → 已预约
     → 已到诊 → 已反馈 → 下转/继续管理 → 已关闭
```

收费使用 `ChargeItem`、`Invoice`、`Payment`、`Refund`、`DailySettlement` 和 `Reconciliation`。患者余额不能直接修改；任何应收、支付和退费均通过账单与流水产生。

模拟医保适配器实现资格校验、申报、受理、拒绝、结算、退费和对账状态；返回明确的“模拟”标识，任何界面和单据不得将其表述为真实医保结算。

区域健康平台、医保、LIS/PACS 和历史系统均通过稳定端口接入。真实适配器替换模拟实现时不得修改领域状态机和门户契约。

## 5. 三门户业务设计

### 5.1 管理端

管理端提供机构、站点、科室、人员、资质、团队、账号、居民主索引、排班模板、服务包、公卫规则、药品目录、库存盘点、收费目录、模拟医保、审计和集成运维能力。

所有关联录入使用可搜索的脱敏实体选择器，不允许要求用户填写数据库 ID。管理看板展示真实更新时间、统计口径和下钻条件，不使用前端当前列表长度推导全局指标。

### 5.2 医护端

- 医生：今日接诊、居民时间线、病历、诊断、处方、检查申请、转诊和复诊计划。
- 护士：签到分诊、生命体征、护理记录、公卫随访、异常复测和上门任务。
- 药师：待审处方、审核意见、调配、核对、发药、退药和药学指导。
- 家庭医生团队：签约居民、待履约任务、风险分层、逾期随访和异常处置。

工作列表必须由服务端分页、筛选、排序和统计。取消、作废、退药、退费等不可逆操作必须填写原因并二次确认。

### 5.3 居民端

居民端提供实名资料、家庭与监护代办、家庭医生签约、服务包履约、真实号源预约、健康档案首页、已签署门诊记录、检查报告、处方和用药指导、随访问卷、自测指标、转诊进度、消息、咨询留言、评价以及授权相关申请。

居民自测记录必须显示来源和“未经医护核验”状态。当前浏览器计算的健康评分、虚构履约百分比和无依据的“正常”结论全部移除。页面只展示原始数值、单位、时间、来源、核验状态以及经审核规则生成的提示和行动建议。

## 6. 安全、隐私与审计

### 6.1 认证与会话

生产门户使用 `HttpOnly + Secure + SameSite` Cookie，不在 `localStorage` 保存访问令牌。短时访问令牌配合 Redis 中的可撤销刷新会话；状态变更请求启用 CSRF 防护。

系统实现登录限流、连续失败锁定、验证码升级、空闲超时、设备会话和全端退出。管理员、医生、护士和药师强制 MFA；居民敏感操作进行再次验证。

Prod 通过一次性命令初始化首个管理员。命令只允许在用户表为空时执行，从标准输入或外部 Secret 获取初始密码，强制首次登录改密，且不在日志中输出密码。

### 6.2 RBAC 与 ABAC

RBAC 决定岗位可执行的动作，ABAC 根据机构、站点、团队、签约、接诊、转诊或明确授权关系决定可访问的数据范围。

- 医生访问本人接诊、本人团队签约或明确授权的居民。
- 护士只能执行护理、公卫和被授权的采集工作。
- 药师可审方、发药，但不能修改医生病历。
- 普通管理员默认不能读取完整病历正文。
- 居民只能访问本人或已验证监护关系下的家属数据。

紧急访问要求填写理由、限定时间和数据范围、再次 MFA，并产生高优先级审计和事后复核任务。

### 6.3 敏感数据与审计

身份证、手机号、地址、诊断和病历按级别分类。列表默认脱敏；查看完整字段需要独立权限。高敏字段使用应用层信封加密，密钥来自外部密钥管理配置。

审计覆盖登录、失败、锁定、会话、查询、创建、修改、更正、作废、病历签署、处方签署、审方、发药、转诊、导出、打印、共享、紧急访问、权限和规则变更。

审计使用只追加表，业务接口无删除能力，并定期归档到防篡改对象存储。审计失败时，病历签署、处方、导出和权限变更等高风险操作失败关闭。

## 7. API、错误与一致性

- API 使用显式版本前缀，例如 `/api/v1`。
- HTTP DTO 与持久化实体分离；由 OpenAPI 生成前端类型和客户端。
- 写入接口支持 `Idempotency-Key`。
- 更新使用实体版本或 `If-Match`；顺序覆盖冲突返回 409。
- 字段校验错误返回结构化 400。
- 无权限返回 403；不可见资源与不存在资源统一返回 404，减少对象枚举。
- 外部依赖使用超时、有限重试、熔断、死信和对账，不进行无限同步等待。
- 前端分别维护 `loading / empty / error / stale / success`；部分失败不能呈现为真实零值或全量成功。
- 时间保存为带时区语义的时间戳，业务逻辑注入 `Clock`，避免直接散布系统当前时间调用。

## 8. 适老化与可访问性

- 居民端移动优先；医护和管理端支持桌面和平板。
- 正文默认不小于 16px，触控目标不小于 44×44px。
- 支持键盘、屏幕阅读器、200% 放大、高对比度和减少动画。
- 表单包含可见标签、单位、格式说明、错误摘要和焦点定位。
- 图表同时提供数据表，不能只通过颜色传达含义。
- 服务电话、机构名称、地址和工作时间由机构配置；电话使用可拨打链接，并区分普通咨询与急救。

## 9. 版本路线

### R0：现有系统安全化

移除虚构健康结论；修复部分失败误报成功、趋势缺失值、历史预约时间校验；配置机构信息；收紧 Actuator；引入 OpenAPI、前端测试、MySQL Testcontainers 和 Flyway 空库测试。

验收结果：可用于虚构数据公开 Demo，不宣称真实诊疗能力。

### R1：真实数据底座

完成机构、人员、居民主索引、家庭监护、账号生命周期、MFA、RBAC + ABAC、脱敏加密、审计、三个前端构建入口和公网/内网隔离。

验收结果：允许不涉及诊断和处方的真实居民档案与健康管理试用。

### R2：预约到接诊闭环

完成排班号源、原子占号、签到候诊、接诊、病史、过敏、诊断、病历签署、更正链和模拟 LIS/PACS。

验收结果：形成线下社区门诊最小闭环。

### R3：处方、药房、收费与模拟医保

完成处方审方、调配发药、批次效期、库存流水、账单支付、退费日结、模拟医保和对账。

验收结果：形成诊疗、药房和收费闭环。

### R4：家庭医生与首批公卫

完成家庭医生团队、签约服务包、履约任务、高血压、2 型糖尿病、COPD、老年人年度管理、异常处置和绩效指标。

验收结果：形成社区医疗医防融合核心能力。

### R5：转诊、区域协同与运营

完成双向转诊、区域平台与真实厂商适配器替换机制、居民档案开放、消息评价、接口工作台和运营质控看板；随后扩展妇幼、儿童、接种、精神卫生和结核模块。

## 10. 质量门禁与上线策略

每个版本必须通过：

- 领域状态机单元测试。
- ArchUnit 模块边界测试。
- Spring Boot API、数据隔离和审计集成测试。
- Testcontainers MySQL 并发、约束、索引和 Flyway 测试。
- OpenAPI 前后端契约检查。
- Vue 组件测试与 Playwright 三门户 E2E。
- axe 无障碍检查。
- 依赖和基础安全扫描。
- 占号、工作列表和居民时间线的性能测试。
- 备份恢复、升级和回滚演练。

新模块使用 Feature Flag 灰度。Demo 与 Prod 使用完全独立的构建、数据库、密钥、对象存储和通知通道。生产先在一个服务站灰度，再扩展至整个中心。病历、处方、发药等高风险功能只有在培训、权限、审计和备份验收后开放。

数据库迁移采用向前兼容的扩展—迁移—收缩策略。已应用的 Flyway 文件不修改；破坏性字段删除至少跨一个发布窗口，并在删除前验证无旧版本实例访问。

## 11. 首轮明确不做的内容

- 不开展互联网首诊或互联网复诊。
- 不在首轮接入当地真实医保、区域平台和 LIS/PACS 接口。
- 不迁移旧系统数据。
- 不拆分微服务，不引入分布式数据库事务。
- 不以 AI 自动生成诊断或处方。
- 不在 R4 之前同步建设妇幼、儿童、接种、精神卫生和结核全套模块。
- 不把模拟医保表述为真实结算。

## 12. 成功判定

平台完成 R0—R5 后，应能在单个社区卫生服务中心及下属站点完成以下可审计闭环：

1. 居民建立唯一档案并完成家庭医生签约。
2. 居民从真实号源预约，到站签到并由授权医生接诊。
3. 医生签署病历和诊断，必要时开具处方、检查或转诊。
4. 药师审核处方，按批次发药并形成库存流水。
5. 收费和模拟医保形成账单、支付、退费与对账记录。
6. 高血压、糖尿病、COPD 和老年人任务按规则生成、执行、异常处置并计入履约指标。
7. 转诊完成接收、到诊、反馈、下转或关闭，不停留在单向申请。
8. 居民可查看本人已开放记录、履约进度和授权状态。
9. 每次敏感访问和高风险操作均可追溯到用户、岗位、目的、时间、数据范围和结果。
10. Demo 密码预填持续可用，但无法进入或影响任何生产数据和密钥环境。
